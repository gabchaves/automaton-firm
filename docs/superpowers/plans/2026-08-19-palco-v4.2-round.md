## Task 1: Empresa — actually fix the crowding (OrgGraph.tsx)

Diagnose first, don't assume the dagre integration is correctly wired — read
the current OrgGraph.tsx in full. Known prior report caveat: "B1's clipping
fix relies on fitView re-run + minZoom=0.1 rather than a hard architectural
cap, so a truly unbounded Encerrados row would eventually render very small
rather than clip" — this is very likely the ACTUAL problem: zooming out to
fit everyone makes every node tiny and unreadable, which reads as "amontoado"
even though nothing technically overlaps anymore.

Fix direction (adjust based on what you find): stop trying to fit the ENTIRE
graph (RH + Firma + Controle + Encerrados) into one viewport at a legible
zoom. Instead:
- Give the "Encerrados" tier its own SCROLLABLE sub-container (independent
  vertical or horizontal scroll, fixed reasonable node size, no forced
  zoom-to-fit shrinking it) separate from the live RH/Firma/Controle graph,
  which stays at a fixed comfortable zoom (e.g. 1.0, or fitView bounded to
  ONLY the live tiers, with minZoom raised so nodes never shrink below a
  legible size).
- Alternative if that's cleaner given the current code shape: keep xyflow for
  the live tiers only (RH + Firma + Controle, which have a small bounded
  size — the roster caps at 5 per cohort), and render "Encerrados" as a
  plain scrollable list/grid BELOW the graph (not a graph node row at all)
  — it doesn't need edges or positioning logic, just needs to be readable
  and scrollable. This sidesteps the unbounded-row-in-a-fitted-viewport
  problem entirely.
- Whichever direction: increase spacing between nodes/tiers generally (the
  "amontoado" complaint suggests current gaps are too tight even for the
  live tiers), and make sure the RH tier has clear visual breathing room
  from the trader tiers below it.

Test: a regression test with 15+ Encerrados entries must prove every node
renders at or above a legible minimum size/zoom (not just "no overlap" like
the previous round's test — that one passed while still being too small to
read, which is the actual bug). If Encerrados becomes a plain list instead
of graph nodes, test that it renders all entries without a graph library at
all and is independently scrollable from the page (page itself must never
scroll horizontally).

## Task 2: Mural — more text variety + pagination

### 2a. More variety
`muralVoice.ts` pools are already at 4-5 variants per type from the last
round — push further where it reads repetitive: add 2-3 more variants to the
highest-frequency post types specifically (trade_closed profit/loss are the
most common event type by far, per the feed). Keep the deterministic
per-event-id seeding contract. Keep rotation posts evidence-blind (never a
performance verdict).

### 2b. Pagination — "páginas para salvarmos mais comentários"
Today `computeFeed`/`org.history` in src/motor/palco-data.ts caps at the 40
newest events (FEED_LIMIT). The user wants to browse further back, not just
lose everything older. Add pagination to the feed:
- Backend: a new SSE-independent endpoint or an extension of the existing
  `/api/snapshot` — simplest: add `GET /api/feed?before=<eventId>&limit=20`
  to scripts/palco-server.mjs, backed by a new exported function in
  src/motor/palco-data.ts (e.g. `fetchFeedPage(raw, { beforeId, limit })`)
  that returns older events (id < beforeId, same html/payload shape as
  `feed`, ordered newest-first) — pure SELECT, same escaping/formatting
  path as computeFeed (reuse formatEventPt). Read the existing server code
  (scripts/palco-server.mjs) first to match its patterns (readonly db open,
  JSON response, error handling).
- Frontend: MuralTab gets a "carregar mais" (load more) control at the
  bottom of the scrap list — clicking it fetches the next page via the new
  endpoint and appends older posts (same post-building logic — trade
  grouping, karma, voice pools — applied to the newly fetched batch too;
  extract/reuse the existing post-building function rather than duplicating
  it). Keep it simple: no infinite scroll requirement, a manual button is
  fine and matches the Orkut-era "ver mais" convention.
Tests: backend fetchFeedPage returns older events correctly paginated
(seed >40 events, verify beforeId/limit slicing, ordering); frontend "load
more" appends without duplicating or losing already-rendered posts.
